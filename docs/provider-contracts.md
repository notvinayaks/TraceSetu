# Provider contracts and acquisition limits

Primary documentation consulted on 24 September 2026. API entitlements and availability remain provider-controlled. Tests in `tests/test_providers.py` use explicitly constructed response fixtures; they are parser/transport regression tests, not evidence of successful live access.

| Adapter | Official contract | Implemented scope and explicit gaps |
|---|---|---|
| Esplora (Bitcoin) | [Blockstream Esplora API](https://github.com/Blockstream/esplora/blob/master/API.md) | Confirmed address history pages; retains transaction input addresses, spent outpoints and output indexes. Continuation requires the actual outpoint. Same-address activity is insufficient. Scripts without address representations, change/ownership clustering and reorganisation reconciliation remain gaps. |
| Etherscan V2 | [ERC20 account endpoint](https://docs.etherscan.io/api-reference/endpoint/tokentx), [receipt](https://docs.etherscan.io/api-reference/endpoint/ethgettransactionreceipt), [block](https://docs.etherscan.io/api-reference/endpoint/ethgetblockbynumber) | Normal/internal indexes and receipt-reconciled standard ERC20 logs for chain IDs 1, 56 and 137. Requires configured key/plan. Token logs bind to receipt success, transaction/block identity, transaction index, log index and acquired block timestamp. Removed or inconsistent logs are rejected. Missing receipt/budget does not fall back to the token-index row. Fixed-head acquisition/internal reconciliation remain incomplete; coverage stays partial. |
| Etherscan metadata | [Address metadata endpoint](https://docs.etherscan.io/api-reference/endpoint/getaddresstag) | Optional, disabled by default. Documentation restricts access to Pro Plus and 2 calls/second. Current nametags are imported as hypotheses, never as established historical ownership or legal-entity identity. The source's explicit exchange category is preserved; deposit acceptance is not invented. |
| TronGrid | [TRC20 account history](https://developers.tron.network/reference/get-trc20-transaction-info-by-account-address) | Confirmed native and TRC20 records, bounded time and fingerprint pages. Approval records are excluded. Internal TRX and precise event ordering remain partial. |
| Solana RPC | [getTransaction](https://solana.com/docs/rpc/http/gettransaction), [getSignaturesForAddress](https://solana.com/docs/rpc/http/getsignaturesforaddress) | Finalized signatures, parsed supported outer/inner transfers, owners from transaction-local token balances. Historic/closed token-account discovery, unsupported instructions and intra-slot ordering remain incomplete. |
| Circle CCTP V2 + Etherscan | [Messages](https://developers.circle.com/api-reference/cctp/all/get-messages-v2), [public keys](https://developers.circle.com/api-reference/cctp/all/get-public-keys-v2), [destination log lookup](https://docs.etherscan.io/api-reference/endpoint/getlogs) | Optional native-USDC Ethereum/Polygon correlation; source bytes, signatures, destination receipt and mint required. Current-key identity and provider/consensus trust remain explicit. Shares the job request budget. Disabled by default; synthetic transport/workflow tests pass, live validation pending. Full contract in `docs/cctp.md`. |

Each acquisition has a request ceiling, response size ceiling, timeout and raw-response content hash. Same-request caching is limited to the acquisition. Provider keys are not returned through capability APIs or stored in request metadata. Errors are reduced to provider/status/error type rather than exposing credential-bearing URLs. No TLS verification is disabled.

The current adapters do not independently reconcile reorganisations. A provider's confirmed/finalized field is recorded at collection time, not treated as a permanent chain fact. A later reconciliation worker and superseding snapshot/report policy are production requirements.

The EVM token decoder follows the [ERC-20 event shape](https://eips.ethereum.org/EIPS/eip-20) and [Ethereum receipt contract](https://ethereum.org/developers/docs/apis/json-rpc/#eth_gettransactionreceipt). It excludes ERC-721's different indexed layout and does not infer unsupported token semantics. Receipt-to-block agreement is a consistency check within the provider's acquired responses, not a consensus/light-client or receipts-trie proof. Decimals remain provider metadata. A contract can emit misleading events: a matching log does not establish token legitimacy, economic value, balance movement or sender authorisation. A reviewed asset registry and stronger token validation remain production gates.

The base deployment does not claim a licensed, comprehensive identity database. Approved agency assertions provide attribution input. Optional metadata is a reviewed-source input, not an automatic legal recipient directory. No contacts are scraped, guessed, or messaged.

## Explicit Bitcoin alternative — 25 September 2026

`ATLAS_BITCOIN_PROVIDER=blockcypher` selects the public full-address endpoint described by [BlockCypher](https://www.blockcypher.com/dev/bitcoin/#address-full-endpoint). It is never a silent fallback. Confirmation checks run locally; exact output satoshis, complete input/output arrays and input outpoints are required. The adapter retains raw hashes, pagination checkpoints, hard budgets and partial coverage. An absent history-completion flag cannot be treated as complete history. The public WannaCry sample produced two transactions and three outputs with no supported service label. Nine provider regression cases and the 116-test full suite passed. The source, exact amounts and actual runtime limits are in `docs/TRACESETU_SUBMISSION.md`.
